# Cam Studio — notes for Claude Code

A Camo Studio–like app: external cameras (USB webcams, Android phones, iPhones) published as a Windows 11
virtual camera **"Cam Studio"** at each source's **native resolution**. User-facing docs: [README.md](README.md)
(Vietnamese). Wire protocol shared by all three sides: [docs/protocol.md](docs/protocol.md).

## Ground rules

- The user writes in **Vietnamese**: reply in Vietnamese. UI strings are Vietnamese too.
- **Clean-room:** all code is our own. Camo Studio may only be studied at a high-level architecture level;
  never copy its code and never bypass its Pro licensing.
- Phone apps are **native per platform** (Kotlin/Camera2, Swift/AVFoundation). They share only the
  protocol spec and the test vectors, not code.
- Keep the PC app light: no per-frame work when nobody consumes the virtual camera.

## Layout and where each part builds

| Part | Path | Builds on | How |
|---|---|---|---|
| Engine (C++, Media Foundation capture, H.264/HEVC decode, phone link, C API) | `src/engine` | Windows only | `scripts\build.ps1` (CMake + MSVC) |
| Virtual camera media source (COM DLL loaded by Frame Server) | `src/vcam` | Windows only | same; install with `scripts\register.ps1` (admin) |
| Shared PC headers (shared memory, NV12 ops, MF devices) | `src/common` | Windows only | — |
| PC app (WinUI 3, C#, .NET 10, unpackaged) | `app/` | Windows only | `scripts\build.ps1` |
| Verify tool, protocol test, fake phone | `src/verify`, `tools/` | Windows only | `scripts\build.ps1` |
| Fake PC (tests a phone app end to end: pair, caps, stream, decode, PNGs) | `tools/fake_pc.swift` | **macOS** | `scripts/fake-pc.sh --lens all` |
| Android app (Kotlin, Camera2 + MediaCodec) | `android/` | Windows, **macOS**, Linux | `cd android && ./gradlew assembleRelease` (JDK 17, Android SDK 36) |
| iPhone app (Swift, AVFoundation + VideoToolbox + Network.framework) | `ios/` | **macOS** (Xcode via XcodeGen), or Linux/WSL via xtool (no screen sharing) | `scripts/ios-run.sh` (tests, build, install, launch); see [ios/README.md](ios/README.md) |
| iPhone screen sharing (ReplayKit broadcast upload extension) | `ios/CamStudioScreen` | **macOS** (Xcode only) | built and embedded with the app |
| Protocol spec + test vectors | `docs/` | — | vectors regenerated by `tools/protocol_vectors.py` |

On a Mac you can work on: the Android app, the iOS app, the protocol/docs. The PC side (engine, vcam,
WinUI app) only builds and runs on Windows 11; on a Mac, `tools/fake_pc.swift` stands in for it.

On this Mac, `xcode-select` points at the command-line tools: use
`DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` (the scripts do this themselves).

## Protocol in one paragraph

The phone is the server. It advertises `_camstudio._tcp` over mDNS on fixed port 47321 (falls back to a
random port). Pairing uses ECDH P‑256 with a 6‑digit numeric comparison code that **both** PC and phone
must accept, then HKDF‑SHA256 (hand-written on every platform, RFC 5869) and AES‑256‑GCM with strict
per-direction counters. Records: CONTROL (JSON), VIDEO_CONFIG, VIDEO_FRAME (Annex‑B H.264/HEVC).
The phone sends `caps` (every lens with its controls, every encoder-supported mode). The PC builds its
UI from caps and sends `set` messages, and the phone streams `state`/`stats`. Bitrate adapts.
Every crypto implementation must match `docs/protocol-vectors.json` byte for byte:
- PC: `build\Release\camstudio-protocol-test.exe` (run from repo root).
- Android: `./gradlew testDebugUnitTest` (`CryptoTest`).
- iOS: `CryptoTests`, scheme `CryptoTestsMac` runs it on the Mac itself:
  `xcodebuild test -project ios/CamStudio.xcodeproj -scheme CryptoTestsMac -destination platform=macOS`.
  XCTest can't run under xtool on Linux.

## Status (2026-10-17)

Verified on real hardware:
- USB webcam (OBSBOT Meet SE) 1920×1080@100 through the virtual camera, checked with `camstudio-verify`.
- Redmi 9T (MIUI, Android) over Wi‑Fi: discovery, pairing, streaming, auto-rotation.
  - Lens chips in the PC overlay: **0.6×** (ultra-wide, hidden camera id 4), **1×** (id 0), **Macro**
    (hidden id 3), and the front camera (id 1). All four stream; the virtual camera delivered native
    1080×1440@30.
- PC idle CPU is about 1.4 % of one core; RAM about 120–140 MB.

iOS app, verified on an iPhone 14 (iOS 27.2, Xcode 27) against `tools/fake_pc.swift` on a Mac:
- `CryptoTests` PASS.
- mDNS discovery and add-by-IP, pairing with the 6-digit code, reconnect with the saved key.
- Lenses `back-dualWide` (virtual), `back-wide`, `back-ultraWide`, `front-trueDepth`.
- Modes: 1080p30/60 H.264, 4K30 HEVC at 25 Mbps, HEVC 10-bit HLG. Every frame decoded, limited range.
- Controls: zoom (with lens switching), torch, tap focus/exposure, manual ISO/shutter/WB/focus, stabilization.
- Cinematic toggled live on `back-dualWide` and `front-trueDepth`; the system video-effects panel
  while streaming; rotation (0/180 in landscape); background then foreground.
- Screen sharing (`CamStudioScreen` extension, second service on port 47322): 888×1920 ~30 fps H.264
  and HEVC, other apps in front, both landscape directions, a still screen, the camera alongside.
- The user's Windows PC paired with the iPhone and streamed 4K from `back-dualWide`. The PC's
  controls and the screen source on the real PC are not yet checked.

## Things learned the hard way

- **MIUI hidden cameras:** the ultra-wide and macro aren't in `cameraIdList`, but they open by id.
  `CameraCaps.hiddenLenses()` handles this:
  - It probes ids 0..63 and test-opens each candidate.
  - It de-duplicates by facing + field of view. Id 5 is a binned duplicate of the main camera.
    **Opening id 5 leaves id 0 "unknown device"** until another lens is opened.
  - When there are two tiny sensors, it drops the one without a flash: that is the B/W depth sensor.
- **PC lens switching:** a phone reports "started" before the camera really opens. The PC only treats a
  lens switch as successful once frames arrive (`FramesCaptured > 0`). Otherwise it marks the lens broken
  and goes back to the previous one.
- **A lost source must not take the virtual camera down.** Apps like Discord drop a camera that disappears.
  - Once the virtual camera is up, `CaptureEngine::Run` keeps it registered when the source goes away:
    phone app hidden, Wi‑Fi lost, webcam unplugged or taken by another app.
  - The engine enters state `Waiting` (4) and retries every 2 s. For a phone, `PhoneLink::Reconnect()`
    reconnects silently: never pairing, and re-resolved by device id.
  - Meanwhile the DLL shows its "no signal" picture.
  - Errors before the camera first starts still fail at once. The lens-switch revert relies on that.
  - Tested on 2026-10-17 by killing and restarting `camstudio-fake-phone` while Discord was using the camera.
- **`E_ACCESSDENIED` (0x80070005) from `IMFVirtualCamera::Start`:**
  - Cause: a **DirectShow** app (Discord loads `ksproxy`/`quartz`) keeps its graph on the old virtual camera
    after we recreate it (source/size change). Frame Server then refuses the new instance until that app
    lets go or Frame Server restarts.
  - Reproduce with `camstudio-dshow-consumer` (`tools/dshow_consumer.cpp`).
  - Fix: `Pipeline::End` calls `IMFVirtualCamera::Remove()` before `Shutdown()`, and `Begin` retries a denied
    `Start` with a fresh registration. Verified on 2026-10-17: switching webcam ↔ phone while the DirectShow
    consumer held the camera.
  - The error bar still offers "Khởi động lại dịch vụ camera" as a last resort.
- **Testing the virtual camera like an app does:** `camstudio-verify` options:
  - `--mode N`: read a given format (e.g. 30 fps like Discord);
  - `--hold S`: stay open, logging every 2 s;
  - `--reopen S`: reopen whenever it disappears.

  It prints no-signal frames and the min/max frame interval.
- **Android encoder:** some vendors reject optional MediaFormat keys, so `CameraStreamer.encoderFormat` has
  three fallback levels.
- **Android app lifecycle:** the app must stay in the foreground. Android blocks the camera for
  background apps, and the PC shows a "background" error when that happens.
- **Android signing:** the release APK is signed with the machine's *debug* keystore. An APK built on another
  machine can't install over one built on Windows: uninstall first, or reuse the same `~/.android/debug.keystore`.
- **iOS:** one shared [ios/Info.plist](ios/Info.plist) serves both xtool (`xtool.yml` `infoPath`) and Xcode
  (`project.yml` `INFOPLIST_FILE` + `GENERATE_INFOPLIST_FILE`). Keep permission strings and
  `NSBonjourServices` there. Without the local-network keys, Bonjour fails silently.
- The cinematic-video API is guarded with `#if compiler(>=6.2)` in `ios/CamStudio/Cinematic.swift`.
- **iOS crashes are Objective-C exceptions**, not Swift errors: `try?` does not catch them. Ones hit on
  the iPhone:
  - `JSONSerialization` with a NaN: `exposureDuration` is invalid for a moment after switching to
    manual exposure. `state` skips non-finite numbers, and `sendControl` checks `isValidJSONObject`.
  - `AVCaptureVideoDataOutput.videoSettings` with a pixel format the output does not list. The list
    is only right after input, camera format and output are all in the session (10-bit for HLG).
  - `temperatureAndTintValues(for:)` with gains outside 1...max, while the session reconfigures.
- **Xcode 27 rewrote `ios/Info.plist`** when the project was opened, moving keys into build settings;
  the next `xcodegen` then dropped them, and the app lost its camera and local-network descriptions.
  Restore with `git checkout ios/Info.plist`. The signing team lives in the git-ignored
  `ios/Signing.local.xcconfig` (via `Signing.xcconfig`), so `xcodegen` never loses it.
- **iOS foreground:** `.inactive` still counts as on screen (the system video-effects panel makes
  the app inactive and the camera keeps running). Only `.background` stops the stream.
- **iOS listener:** iOS reclaims listening sockets while the app is suspended, so `PhoneServer`
  starts a new `NWListener` when the app returns from the background.
- **iOS front camera:** TrueDepth and the front wide-angle camera are the same sensor. Only one is
  listed: TrueDepth when it can do cinematic video, which it can on the iPhone 14.
- **iOS screen sharing:**
  - **Bundle id:** `vn.camstudio.phone` belongs to another account and cannot be registered as an
    App ID, so the app runs on the team's wildcard profile. That rules out App Groups. The app and
    the extension share the deviceId and the pairing keys through **Keychain Sharing**
    (`<team>.vn.camstudio.shared`, from `CamStudioKeychainGroup` in Info.plist).
  - **Identity on the PC:** the screen advertises TXT `id=<deviceId>:screen` so the PC (which keys
    sources by host:port) treats it as a separate source, while `hello` keeps the real deviceId for
    the pairing key. `PhoneLink::Reconnect` therefore looks a link up again by the TXT id it was
    found under, not the hello id; that change was written on the Mac and is **not compiled yet**.
  - **Orientation:** `RPVideoSampleOrientationKey` is the opposite of its EXIF meaning (`.right`
    needs 270°), as measured.
  - **ReplayKit buffers:** 888×1920 on the iPhone 14, and a frame only when the screen changes.
    The extension re-sends the last frame and starts from the newest one, because the PC drops a
    source that is silent for 6 s.
  - **Reinstall:** reinstalling the app ends a running broadcast; the person has to start it again.
- **The phone serves one PC at a time:** a new connection replaces the old one. A test from the
  fake PC on the Mac kicks the user's real Windows PC off (and the PC's reconnect kicks the fake
  PC). Ask before testing while the user's PC may be streaming.
- **Any `error` ends the PC's stream** (`CaptureEngine::RunPhone`). So a `set` the phone cannot apply
  (e.g. cinematic on a lens without it) is reported through `state`, not `error`.
