# Cam Studio — notes for Claude Code

> **Unfinished work (2026-10-18): read [docs/HANDOFF.md](docs/HANDOFF.md) first.** It says what is
> not tested yet, the user's decisions, and the next steps.

A Camo Studio–like app: external cameras (USB webcams, Android phones, iPhones) published as a Windows 11
virtual camera **"Cam Studio"** at each source's **native resolution**. User-facing docs: [README.md](README.md)
(Vietnamese). Wire protocol shared by all three sides: [docs/protocol.md](docs/protocol.md).

## Ground rules

- The user writes in **Vietnamese**: reply in Vietnamese. UI strings are Vietnamese too.
- **Clean-room:** all code is our own. Camo Studio may only be studied at a high-level architecture level;
  never copy its code and never bypass its Pro licensing.
- Phone apps are **native per platform** (Kotlin/Camera2, Swift/AVFoundation). They share only the
  protocol spec and the test vectors, not code.
- Keep the PC app light: no per-frame work when nobody consumes the virtual camera.
- **Git: one branch only, `main`** (the user's rule, 2026-10-18):
  - Work and commit directly on `main` in the main checkout. Push only `main`.
  - Create no other branch and no worktree. Do not start sessions or agents in a worktree
    (`use_worktree: false`, no `isolation: "worktree"`).
  - If a tool or session still creates one: before the session ends, merge it into `main`, push
    `main`, and delete the branch (local and remote) and the worktree. Leave nothing behind.
  - Keep notes short. The user does not want to read much.

## Protocol in one paragraph

The phone is the server. It advertises `_camstudio._tcp` over mDNS on fixed port 47321 (falls back to a
random port). Over a USB cable the PC reaches the same port through a tunnel (adb for Android, usbmuxd for
iPhone; docs/protocol.md 1.2), with the same handshake. Pairing uses ECDH P‑256 with a 6‑digit
numeric comparison code that **both** PC and phone must accept, then HKDF‑SHA256 (hand-written on every
platform, RFC 5869) and AES‑256‑GCM with strict per-direction counters. Records: CONTROL (JSON), VIDEO_CONFIG, VIDEO_FRAME (Annex‑B H.264/HEVC).
The phone sends `caps` (every lens with its controls, every encoder-supported mode). The PC builds its
UI from caps and sends `set` messages, and the phone streams `state`/`stats`. Bitrate adapts.
Every crypto implementation must match `docs/protocol-vectors.json` byte for byte:
- PC: `build\Release\camstudio-protocol-test.exe` (run from repo root).
- Android: `./gradlew testDebugUnitTest` (`CryptoTest`).
- iOS: `CryptoTests`, scheme `CryptoTestsMac` runs it on the Mac itself:
  `xcodebuild test -project ios/CamStudio.xcodeproj -scheme CryptoTestsMac -destination platform=macOS`.
  XCTest can't run under xtool on Linux.

### Windows 10 support (2026-10-18, DirectShow) — see [docs/windows10.md](docs/windows10.md)

Windows 10 has no `MFCreateVirtualCamera`. The engine looks the API up at run time
(`VirtualCameraApi()` in `CaptureEngine.cpp`); absent, it writes NV12 frames to a **session-local**
shared-memory channel (`CAMSTUDIO_LOCAL_*` in `SharedFrame.h`) and a **DirectShow source filter**
(`src/dshow`) inside the capturing app reads them. `CAMSTUDIO_FORCE_DSHOW=1` forces this path on
Windows 11.
- The filter is built x64 **and** x86 (`scripts\build.ps1` adds `build-x86`): a 32-bit app loads a
  32-bit filter. `regsvr32` registers it (HKLM elevated, HKCU otherwise).
- Only apps that capture through **DirectShow** see it on Windows 10 (Discord, OBS, Zoom, Chrome).
  Media-Foundation-only apps (the Windows Camera app) do not.
- **Floor: Windows 10 2004 (build 19041), x64 only.** The engine statically imports
  `DnsServiceBrowse`/`Resolve` (mDNS, added in 18362), so 1809 can't load it. No 32-bit Windows, no
  ARM. The installer picks the MF camera on Windows 11 (`IsWindows11`) or the two DirectShow DLLs on
  Windows 10.
- `tools/dshow-consumer --grab [--fourcc YUY2|I420]` measures the delivered frames (no window).
- **Tested** on Windows 11 only, through the forced path: x64 and x86 filters deliver live
  NV12/YUY2/I420 (consumer `--grab`), and the MF path still passes `camstudio-verify` (180/180 live).
  **Not tested on a real Windows 10 PC**, but **published in v0.1.6** (installer built here and
  installed on the user's Win11 PC; the iPhone then streamed 2K/60). **v0.1.7** (2026-10-19: new PC
  interface, colour presets, restart button, face framing) is installed on the user's PC and
  **published** (2026-10-20). **v0.1.8** (2026-10-20: effects, snapshot/recording, pause picture,
  global shortcuts, hot phone, QR, forget a phone, Fluent icons) is **published** (tag on d7ac5cd);
  the installed 0.1.7 found it and offered the update. **v0.1.9** (2026-10-21: phone microphone,
  Android) is **published** (tag on 07218c5). The `DllCanUnloadNow` is `S_FALSE`, so
  once anything (even the Claude desktop app's device enumeration) loads the registered filter DLL it
  stays mapped and locks the file: rename the DLL aside before rebuilding, or unregister first.
- **iPhone pairing (same day):** when the PC and phone hold **different** pairing keys (app
  reinstalled, or paired elsewhere), the phone closes cleanly on the PC's auth MAC. The PC now marks
  the link `"pair"` only on that **clean close** (`ReadHandshake` surfaces `timedOut`), not on
  timeouts; picking the phone re-pairs with the 6-digit code (`PhoneLink::Connect` retries with
  `repair`, sends `pairStart` though both claim a key). iOS `Store` was tightened too (not compiled
  here — needs a Mac build). A suspended/locked iPhone instead **does not answer hello at all**.

## Things learned the hard way

- **MIUI hidden cameras:** the ultra-wide and macro aren't in `cameraIdList`, but they open by id.
  `CameraCaps.hiddenLenses()` handles this:
  - It probes ids 0..63 and test-opens each candidate.
  - It de-duplicates by facing + field of view. Id 5 is a binned duplicate of the main camera.
    **Opening id 5 leaves id 0 "unknown device"** until another lens is opened.
  - When there are two tiny sensors, it drops the one without a flash: that is the B/W depth sensor.
- **PC lens switching:** a phone reports "started" before the camera really opens. The PC only treats a
  lens switch as successful once frames arrive (`FramesCaptured > 0`). Otherwise it marks the lens broken
  and goes back to the previous one.
- **A lost source must not take the virtual camera down.** Apps like Discord drop a camera that disappears.
  - Once the virtual camera is up, `CaptureEngine::Run` keeps it registered when the source goes away:
    phone app hidden, Wi‑Fi lost, webcam unplugged or taken by another app.
  - The engine enters state `Waiting` (4) and retries every 2 s. For a phone, `PhoneLink::Reconnect()`
    reconnects silently: never pairing, and re-resolved by device id.
  - Meanwhile the DLL shows its "no signal" picture.
  - Since 2026-10-18 the camera lives as long as the app, so there is no
    "fail at once" any more: a source that fails before the camera was published publishes it and
    waits. The lens-switch revert works from `Waiting` (switching back). See the PC subsection below.
  - Tested on 2026-10-17 by killing and restarting `camstudio-fake-phone` while Discord was using the camera.
- **`E_ACCESSDENIED` (0x80070005) from `IMFVirtualCamera::Start`:**
  - Cause: a **DirectShow** app (Discord loads `ksproxy`/`quartz`) keeps its graph on the old virtual camera
    after we recreate it (source/size change). Frame Server then refuses the new instance until that app
    lets go or Frame Server restarts.
  - Reproduce with `camstudio-dshow-consumer` (`tools/dshow_consumer.cpp`).
  - Fix: `Pipeline::End` calls `IMFVirtualCamera::Remove()` before `Shutdown()`, and `Begin` retries a denied
    `Start` with a fresh registration. Verified on 2026-10-17: switching webcam ↔ phone while the DirectShow
    consumer held the camera.
  - The error bar still offers "Khởi động lại dịch vụ camera" as a last resort.
- **Testing the virtual camera like an app does:** `camstudio-verify` options:
  - `--mode N`: read a given format (e.g. 30 fps like Discord);
  - `--hold S`: stay open, logging every 2 s;
  - `--reopen S`: reopen whenever it disappears.

  It prints no-signal frames and the min/max frame interval.
- **Android encoder:** some vendors reject optional MediaFormat keys, so `CameraStreamer.encoderFormat` has
  three fallback levels.
- **Android app lifecycle:** the app must stay in the foreground. Android blocks the camera for
  background apps, and the PC shows a "background" error when that happens.
- **Android signing:** the release APK is signed with the machine's *debug* keystore. An APK built on another
  machine can't install over one built on Windows: uninstall first, or reuse the same `~/.android/debug.keystore`.
- **iOS:** one shared [ios/Info.plist](ios/Info.plist) serves both xtool (`xtool.yml` `infoPath`) and Xcode
  (`project.yml` `INFOPLIST_FILE` + `GENERATE_INFOPLIST_FILE`). Keep permission strings and
  `NSBonjourServices` there. Without the local-network keys, Bonjour fails silently.
- The cinematic-video API is guarded with `#if compiler(>=6.2)` in `ios/CamStudio/Cinematic.swift`.
- **iOS crashes are Objective-C exceptions**, not Swift errors: `try?` does not catch them. Ones hit on
  the iPhone:
  - `JSONSerialization` with a NaN: `exposureDuration` is invalid for a moment after switching to
    manual exposure. `state` skips non-finite numbers, and `sendControl` checks `isValidJSONObject`.
  - `AVCaptureVideoDataOutput.videoSettings` with a pixel format the output does not list. The list
    is only right after input, camera format and output are all in the session (10-bit for HLG).
  - `temperatureAndTintValues(for:)` with gains outside 1...max, while the session reconfigures.
- **Xcode 27 rewrote `ios/Info.plist`** when the project was opened, moving keys into build settings;
  the next `xcodegen` then dropped them, and the app lost its camera and local-network descriptions.
  Restore with `git checkout ios/Info.plist`. The signing team lives in the git-ignored
  `ios/Signing.local.xcconfig` (via `Signing.xcconfig`), so `xcodegen` never loses it.
- **iOS foreground:** `.inactive` still counts as on screen (the system video-effects panel makes
  the app inactive and the camera keeps running). Only `.background` stops the stream.
- **iOS listener:** iOS reclaims listening sockets while the app is suspended, so `PhoneServer`
  starts a new `NWListener` when the app returns from the background.
- **iOS front camera:** TrueDepth and the front wide-angle camera are the same sensor. Only one is
  listed: TrueDepth when it can do cinematic video, which it can on the iPhone 14.
- **iOS screen sharing:**
  - **Bundle id:** `vn.camstudio.phone` belongs to another account and cannot be registered as an
    App ID, so dev builds run on the team's wildcard profile. That rules out App Groups. The app and
    the extension share the deviceId and the pairing keys through **Keychain Sharing**
    (`<team>.vn.camstudio.shared`, from `CamStudioKeychainGroup` in Info.plist).
  - **TestFlight** needs an explicit, registered id, so the id is `$(CAMSTUDIO_BUNDLE_ID)` (extension:
    `.screen` appended). The default is in `ios/Signing.xcconfig`; `Signing.local.xcconfig` overrides
    it. `scripts/ios-archive.sh` refuses the default id and a Personal Team, and checks the archive:
    extension embedded, same version, permission strings present.
  - Automatic signing registers a new id on whatever team signs it, for good. So both scripts
    (`scripts/ios-team.sh`) show the team name and ask before the first build of an id on a team.
    A yes is remembered as `// confirmed: <team> <id>` in `Signing.local.xcconfig`. Dev builds may
    sign with the team's wildcard profile, so a missing explicit profile proves nothing.
  - **Do not pick the team in Xcode's Signing tab:** Xcode writes `DEVELOPMENT_TEAM` into
    `project.pbxproj` (now tracked in git), at project level too, and that overrides
    `Signing.local.xcconfig`. `xcodegen` (both scripts run it) puts the file back.
  - **Privacy manifest:** `ios/Resources/PrivacyInfo.xcprivacy`, copied into both targets. It
    declares `UserDefaults` (CA92.1), the only required-reason API in either binary (checked with
    `nm -u`).
  - **Identity on the PC:** the screen advertises TXT `id=<deviceId>:screen` so the PC (which keys
    sources by host:port) treats it as a separate source, while `hello` keeps the real deviceId for
    the pairing key. `PhoneLink::Reconnect` therefore looks a link up again by the TXT id it was
    found under, not the hello id; that change compiles; not yet tested with the iPhone screen.
  - **Orientation:** `RPVideoSampleOrientationKey` is the opposite of its EXIF meaning (`.right`
    needs 270°), as measured.
  - **ReplayKit buffers:** 888×1920 on the iPhone 14, and a frame only when the screen changes.
    The extension re-sends the last frame and starts from the newest one, because the PC drops a
    source that is silent for 6 s.
  - **Reinstall:** reinstalling the app ends a running broadcast; the person has to start it again.
- **Android screen sharing:** same protocol as iOS (port 47322, TXT `id=<deviceId>:screen`,
  `notPaired`). The pieces:
  - `ScreenService`: a foreground service of type `mediaProjection`. Consent comes from `MainActivity`,
    once per sharing session.
  - `ScreenCapture`: one VirtualDisplay for the whole session (Android 14 allows only one per consent).
    It draws through a SurfaceTexture into OpenGL, then into the encoder surface of each stream.
  - The SurfaceTexture is created detached and is attached only while a stream exists, so no idle
    EGL surface is needed.
  - **Stream shape:** caps offer landscape sizes first, because many Android encoders cap at
    1920×1088 (the Redmi 9T's do, which left `modes` empty with portrait sizes). When the screen
    and the stream differ in shape, GL turns the picture 90° clockwise and reports `orientation` 270.
    The Redmi sends 1920×880 and 1280×592, multiples of 16.
  - The last picture is re-drawn every 250 ms while the screen is still.
  - `Session` streams any `MediaSource` (`CameraSource`, `ScreenSource`), like iOS. `CameraStreamer` is
    unchanged.
  - **Verified 2026-10-17** on the Redmi 9T (Android 12) with the real PC:
    - portrait 880×1920 and both landscape directions upright;
    - the home screen in front;
    - stop, then start again: the PC goes to Waiting, then reconnects to the screen port by itself;
    - camera regression: opening, front/back switch, Home.
  - Side effect: while sharing, the foreground service keeps the camera stream alive with the app hidden.
  - `CrashLog` shows the last crash on the next launch. With USB debugging, `adb` works:
    `%LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe`.
- **The PC writes ~1 frame/s to the virtual camera even with no consumer.** An app that opens it then
  gets a picture at once, even from a slow source like a still phone screen (~4 frames/s), instead of
  the no-signal picture.
- **Standby (the user wants the app as light as possible):**
  - **When it applies:** the virtual camera is on, no app streams from it (`readerActive` in shared
    memory), and the window is hidden or minimized (`m_previewEnabled` false).
  - **What happens:** `CaptureEngine::Run` keeps the virtual camera registered but closes the source.
    The webcam light goes off, and the phone gets `stop`, so it stops encoding.
  - **Waking:** it starts again when an app opens the camera, or when the window shows. It closes
    again after 5 s idle (`kIdleCloseMs`).
  - **Standby size:** a phone source's camera is published at its last known orientation
    (`m_rotationMemory`; first guess 90 for cameras, 270 for an Android screen). This avoids rebuilding
    the camera, which would drop the app that just opened it.
  - **Measured 2026-10-17:**
    - OBSBOT: 0.1% CPU, 43 MB working set. The source woke in ~2.2 s, and was closed again 7 s after
      the app left.
    - Redmi screen: 0.3% CPU, and 0 encoders running on the phone. It woke in ~0.5 s.
  - **Memory:** the app calls `EmptyWorkingSet` when hidden.
  - **Status:** shown through `CsStatus.standby`.
- **USB cable (docs/protocol.md 1.2):** no phone change was needed for the tunnel; it arrives on loopback.
  - **The PC never probes a phone port** to see whether the app is open or sharing its screen. Phone
    apps built with the hello-before-replace change (2026-10-18) are probe-safe (below). Older builds
    drop the session in progress on any accepted connection: every earlier APK, and iOS TestFlight up
    to 20261018.0743. The version numbers did not change (Android 0.1.3, iOS 0.1.0), so they cannot
    tell the two apart.
  - So every phone ready on the cable is listed twice, whether or not it shares its screen:
    "<name> (USB)" on 47321 and "<name> · Màn hình (USB)" on 47322. When nothing listens on 47322,
    adb answers `FAIL` and usbmux `3`, and `OpenAdb`/`OpenUsbmux` say "chưa chia sẻ màn hình".
  - The USB list comes from background watchers (adb `host:track-devices`, usbmuxd `Listen`), never
    from I/O in `KnownPhones()`: `cs_refresh_cameras` runs on the UI thread.
  - A phone is listed only once its name is read (adb `settings get global device_name`, lockdownd
    `DeviceName` without a session), so the name never changes while it is plugged in.
  - usbmux `Connect` takes the port byte-swapped (47321 → 55736). The DeviceID changes on every plug-in:
    look it up by UDID each time.
  - **A suspended iPhone app still accepts a usbmux connection, then never answers** (phone locked, app
    in the background). Later, once iOS reclaims the listener, `Connect` returns 3. `PhoneLink` waits
    8 s for `hello`, then says to unlock the phone and open the app.
  - adb on Windows: started only when no server answers and an ADB interface
    `{F72FE0D4-CBCB-407D-8814-9ED673D0DD6B}` is present. The engine never runs `adb.exe` while a server
    runs (another version would kill it). It stops only the server it started: after a minute with no
    phone on adb (adb scans USB every second), or on exit.
  - A USB link reconnects over the same cable only: unplugged means Waiting, never a silent switch to Wi‑Fi.
- **The phone serves one PC at a time:** a new connection replaces the old one, but only once it has
  sent a valid `hello` (docs/protocol.md 3.1). A test from the fake PC on the Mac kicks the user's
  real Windows PC off (and the PC's reconnect kicks the fake PC). Ask before testing while the
  user's PC may be streaming.
  - **Probe-safe since 2026-10-18** (`PhoneServer` on iOS, shared with the screen extension, and on
    Android): a connection waits apart from `session` until its hello is valid, then `claim`s it.
    One that closes first, sends junk, or is silent for 10 s is closed; the session in progress
    and the status text stay as they were. Android swaps `session` under the lock and closes the
    old one outside it (a camera can take a while to stop).
  - iOS `Connection.readExact` has no timeout, so the 10 s deadline is a main-queue timer that
    cancels the `NWConnection` (that ends the pending receive). Android uses `soTimeout`.
- **Any `error` ends the PC's stream** (`CaptureEngine::RunPhone`). So a `set` the phone cannot apply
  (e.g. cinematic on a lens without it) is reported through `state`, not `error`.

### PC: how many sources work (2026-10-18)

- **The virtual camera lives as long as the app.** The app registers it at launch with no source
  (`cs_switch_none`, at the last size it had: `LastWidth/LastHeight` in the registry) and never
  removes it until exit. No source, or the toggle off ("Tạm dừng hình"): apps see "no signal".
  A source that fails keeps the camera (`Waiting`); a source that fails for good (`Fatal`:
  lens refused, no HEVC decoder, window closed) waits there until another one is picked. Only a
  failed registration ends the session; the app tries again every 30 s.
- **Switching keeps the camera:** `CaptureEngine::Switch` sets `m_switch`; every source loop checks
  `Interrupted()` and returns `Outcome::Switch`; `Run` keeps the `Pipeline`. Until the new source's
  first frame the last picture is **held**: `FrameWriter::HoldFor` moves the latest slot's
  `writeTime100ns` ahead of now (the reader's age check is a signed difference), nothing copied.
  Refreshed while the new source opens; `ReleaseHold` when it is lost.
- **Size rule** (`PlanOutput`, applied in `Pipeline::Relayout` on every frame when something
  changed, and once a second): an app using the camera (or within 5 s: apps restart their stream
  to change mode) keeps its size and other pictures are fitted with black bars; otherwise the
  camera is rebuilt at the picture's own size. Fixed sizes (4K/1080p/720p) fit everything. A
  rebuild refused with `E_ACCESSDENIED` re-registers the old size and stays fitted for 30 s.
  Phone rotation and `SetImage` follow the same rule (no more restarts). The preview shows the
  picture without the bars; `CsStatus.pictureWidth/Height` is its size (tap-to-focus, panning).
- **Background connector** (`Connector`, one thread, every 3 s and on mDNS changes): hello
  `auto`, caps once, drains and pings idle links every 15 s. Waits 30 s after a failure or
  `busy`, 30 s doubling to 8 min after a dropped idle link (old phone apps hand themselves to
  every connection, two PCs would fight), retries at once when the phone reappears. One link per
  phone server (deviceId + camera/screen), the cable preferred; a link in use is never taken.
  Started with Windows (`--tray`): discovery and the connector start after 20 s (`cs_init_delayed`).
- **Lease:** one reader per `PhoneLink` (capture thread, screen window, `cs_load_formats` pairing,
  or the connector). `Lease()` aborts a connector *connect attempt* (`SetAttempting`) but waits for
  a quick idle drain. `Abort()` (any thread) only `shutdown`s the socket; the lease holder closes
  it, so `Close()` no longer races `Receive()`. `SendControl` failing aborts instead of closing.
- **A kept idle link may be dead** (phones don't answer `ping`): TCP keepalive on Wi‑Fi, and
  `RunPhone` reconnects once if nothing at all arrives 4 s after `start`.
- **Sources are known by id** (`cs_camera_id`): `cam:<symbolic link>`, `phone:<ip>:<port>`,
  `phone:usb:<serial>:<port>`. Indices change on every refresh, now also while streaming.
  The mode is remembered per id (`HKCU\Software\CamStudio\Modes`).
- **Micro điện thoại** (2026-10-21, docs/protocol.md 5.1, `AudioOut.cpp`, `MicCapture.kt`,
  `MainWindow.PhoneMic.cs`): the phone's mic as AUDIO records (kind 4, PCM16), asked with `audio` in
  `start` / `set`, gated by `caps.audio` (Android only; iOS not written). The PC plays it into an
  output device, VB-Audio's "CABLE Input" by default, never the speakers. Since 0.1.10 the app
  installs VB-CABLE on a click (see "Thành phần bổ sung"). A phone camera source stays open while hidden when
  an app uses a microphone (ConsentStore `microphone`, `cs_set_audio_wanted`), so a call with the
  camera off keeps the sound; the phone then encodes video too (a later "audio-only start" would
  save that). Tested: fake phone `--audio` → `wav:` target, 28 s of 440.0 Hz, no gap, `set`
  off live. Android: `RECORD_AUDIO` asked at launch, the service adds type `microphone` only once
  granted (else camera alone). **Redmi 9T over USB (2026-10-21):** 48 kHz, nothing lost, also
  with the screen off and locked ("Chạy nền" on; `dumpsys audio` says "not silenced"). Denied:
  the camera streams, the reason shows on the phone and in the PC's mic tooltip (amber dot).
  Not yet seen on a device: the PC's request popping the permission prompt, sound starting
  after a later grant. A WinUI tooltip set again every tick never opens: set it on change only.
- **"Hiệu ứng" › Nền** (2026-10-20, `Segmenter.cpp`, `MainWindow.Background.cs`): blur or an image
  behind the person. Model `app/Assets/Models/pphumanseg.onnx` (OpenCV Zoo PP-HumanSeg 2023mar,
  Apache 2.0, opset 11, IR 8, output softmax; channel 1 = person, checked: an empty room blurs
  whole). Inbox Windows ML on Win11 runs it on the GPU in ~1–2 ms; at 1080p100 the frame work
  went 3.1 → 5.4 ms; RAM +~130 MB once loaded (DirectML stays mapped). Windows 10: untested.
  Dark furniture can pass as a person. Cameras only; a model that fails stays off until "Tắt".
- **"Hiệu ứng" › Làm mịn da** (`SkinSmooth.h`): a self-guided filter on luma inside each face's
  ellipse, faces from its own FaceTracker on the output picture (5/s). `frame-check` covers it
  (noise down, edge kept, outside untouched). Not yet seen on a real face.
- **Hot phone** (2026-10-20, `MainWindow.Thermal.cs`): `state.thermal` serious → the best mode of
  the same lens at ≤1080 (short side) and ≤30 fps, critical → ≤720; once per level and source,
  the saved mode untouched, a warning bar. Tested with `camstudio-fake-phone --thermal serious`
  (it then offers 30 and 60 fps and sends the state 5 s into a stream): 720p60 → 720p30.
- **Snapshot and recording** (2026-10-20, `Recorder.cpp`, `MainWindow.Record.cs`): what the camera
  shows (settings, framing, colour), PNG to Pictures\Cam Studio, MP4 (H.264 through the GPU's MFT,
  AAC from the default microphone, timed by sample count) to Videos\Cam Studio. Up to 60 fps (a
  100 fps webcam gives ~50). A recording or a snapshot keeps the source out of standby
  (`SourceWanted`); paused, the pause picture is recorded. The microphone thread is never shut
  down while it reads (that hung `Stop`): it gets 1 s to see the stop flag. Updates wait for a
  recording to end. Ctrl+Alt+C / Ctrl+Alt+R, the tray (not Ctrl+Alt+S: Zalo takes it).
- **Phone app QR** (2026-10-20, `QrCode.cs`, `MainWindow.Download.cs`): our own encoder (byte mode,
  level M, versions 1–10), checked against Thonky's HELLO WORLD Reed–Solomon codewords and the
  ISO format strings. It encodes the GitHub `releases/latest` page (the APK's name has the
  version). "+" › "Tải app cho điện thoại…", and the empty preview with no source.
- **Pause picture** (2026-10-20, `StillPicture.cpp`, `MainWindow.Pause.cs`): while paused, apps see
  the last picture blurred with "Quay lại ngay" (default), a card, the person's image (copied to
  `%LOCALAPPDATA%\CamStudio\pause-image.*`) or the old "no signal". The app calls
  `cs_set_pause_picture` before every `cs_switch_none` (NoSignal unless paused); the engine renders
  it once (Direct2D) and writes it twice a second with an app on the camera, every 1.5 s without.
- **Global shortcuts** (2026-10-20, `MainWindow.Hotkeys.cs`, `GlobalHotkeys.cs`): `RegisterHotKey`
  on a message-only window, so they work hidden and in a call. Ctrl+Alt+letter by default
  (Settings › Phím tắt: change, Backspace = off, a taken combination says so). Unregistered while
  a row records a new one. Hidden: a silent tray notification says what happened.
  Testing with injected keys (keybd_event): a remote-desktop app in front (UltraViewer on the
  user's PC) swallows Ctrl+Alt combos, so put a window of your own in front first. Zalo owns
  Ctrl+Alt+S. Verified 2026-10-20: hidden + standby, Ctrl+Alt+C woke the webcam and saved a PNG
  in 2.4 s; with `camstudio-verify --hold` as the app on the camera, pause/resume/record kept
  1350/1350 live frames.
- **List order and forgetting** (2026-10-20): sources that work first, phones that can't be used
  now under "Chưa kết nối". Right-click a phone: "Quên ghép đôi…" (deletes the key, closes its
  idle links) and "Xóa khỏi danh sách" (added by IP): `cs_phone_flags` / `cs_forget_phone`. A
  cable phone not connected in this run has no known id, so it has no "Quên ghép đôi". Add by IP
  takes a bare IP (port 47321 by default).
- **Thành phần bổ sung** (0.1.10, `Services/AddOns.cs`, `MainWindow.AddOns.cs`): what Windows
  lacks, installed on one click (an InfoBar when it matters, Settings › Thành phần bổ sung):
  - iPhone on a cable: Apple Devices (Store 9NP83LWLPZ9K) by `winget --source msstore`, hidden, no
    UAC (~22 s). It has **no Windows service**: `AppleMobileDeviceProcess` (127.0.0.1:27015) is
    started by a packaged startup task, and only after Apple Devices was opened once and the
    person clicked **Agree** on Apple's licence (we never click it). "Trust" is not needed: the
    tunnel opens and the name ("Win_Lax") reads without it. `Invoke-CommandInDesktopPackage`
    hangs. Offered when an iPhone (USB VID 05AC, PID 12xx) is plugged in and 27015 is closed.
  - VB-CABLE: the newest official zip from vb-audio.com, Authenticode valid and signed by
    "BUREL VINCENT", then VB's own setup elevated (the person clicks Install Driver). Not silent:
    the package's readme forbids folding it into another setup without the author's consent,
    although vb-audio.com allows bundling with attribution (shown in Settings). On the user's PC
    CABLE Input/Output appeared without a restart.
- **Phone cards** group by the phone's own id (`cs_phone_identity`), else by name; a cable route
  not connected yet joins the only Wi‑Fi phone of the same OS. An iPhone tells apps on Wi‑Fi only
  "iPhone"; the cable (lockdownd) gives the person's name, which the card shows.
- **iPhone over USB on Windows** (2026-10-21, iPhone 14, 1080p30 because it was hot): glass-to-
  glass to the preview ~130 ms over the cable (frame interval 32–35 ms) against ~185 ms on
  Wi‑Fi (16–50 ms). The first cable start right after Wi‑Fi timed out once, then reconnected.
- **Automatic pick** (app, `MainWindow.Sources.cs`): the source picked last, else connected
  phones (cable, then Wi‑Fi), USB webcams, the built-in camera (`EnclosureLocation.Panel`). A
  better one replaces an automatic pick only while no app uses the camera; a source lost for
  10 s is replaced even in a call; a user's pick is never replaced.
- **Phone screen in its own window:** `ScreenViewer` leases the screen's link; one connection per
  screen, so it cannot be the camera and a window at once ("Dùng làm camera ảo" closes the
  window). `ScreenWindow` keeps the aspect with `WM_SIZING` (subclassed with `SetWindowLongPtrW`:
  the manifest has no common controls v6).
- **Window source:** Windows.Graphics.Capture, free-threaded frame pool (the capture thread has no
  dispatcher). Frames are read back from the GPU only when they go somewhere. A resized window
  is fitted into its first size until its new size is steady for 1 s. A still window sends no
  frames: the last one is held. `GraphicsCaptureAccess`/`IsBorderRequired` need a Windows SDK of
  10.0.20348 or newer to compile.
